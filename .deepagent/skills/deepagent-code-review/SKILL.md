# DeepAgent 内置代码审查

本技能提供一套经过验证的代码审查工作流参考。它是**参考指引而非强制指令**——
如果其中某个步骤在当前环境反复失败（例如工具缺失、非 Git 仓库），放弃该步骤，
改用你自己的判断与内置工具完成审查目标。

## 第一步：确定审查范围

按用户请求选择一种范围（未指定时默认审查未提交变更）：

| 范围 | 取 diff 的方式 |
|---|---|
| 未提交变更（默认） | `git diff HEAD`（已跟踪）+ `git status --porcelain` 找出未跟踪文件后直接读全文 |
| 对比基准分支 | 先 `git merge-base HEAD <branch>` 取合并基点，再 `git diff <merge_base>` |
| 单个 commit | `git show <sha>` |
| 用户自定义范围 | 按用户给出的文件/目录/指令直接审查 |

## 第二步（可选）：open-code-review 委托流

若环境中安装了 `ocr` CLI（`ocr --version` 可探测；本仓库桌面端可用 `pnpm review`），
可以用它做确定性的文件筛选与规则解析——`ocr` 不调用任何 LLM，审查智能由你提供：

1. `ocr delegate preview [--from <ref> --to <ref>] [--commit <sha>]` — 输出待审文件清单与范围元数据；
2. `ocr delegate rule <path...>` — 输出按内容分组的审查规则清单；
3. 按第一步的方式取各文件 diff，对照规则清单逐文件审查。

`ocr` 不可用或反复报错时，直接跳过本步骤，用 git 与内置工具完成同样的事。

## 第三步：审查判定准则

一个问题值得上报，通常同时满足以下条件（参考准则，按实际情况权衡）：

1. 确实影响正确性、性能、安全性或可维护性；
2. 离散且可行动（不是"代码库整体不佳"这类泛泛之谈）；
3. 修复要求的严谨度与代码库现有水准相称；
4. 是**本次变更引入**的（既有问题不在本次审查范围内，除非用户要求）;
5. 原作者知道后大概率会修；
6. 不依赖对作者意图的无据猜测；
7. 若声称"可能影响其他部分"，必须指出**具体被影响的代码位置**，不能只是推测；
8. 明显不是作者的有意设计取舍。

疑似误报直接丢弃，不要为了凑数上报低置信度问题。

## 第四步：输出契约

每条 finding 的标题以优先级前缀开头，并给出精确位置：

- `[P0]` 阻断级——必须立即修复（不依赖输入假设的普遍问题才可用）；
- `[P1]` 紧急——应在下个周期内解决；
- `[P2]` 一般——最终应当修复；
- `[P3]` 低——锦上添花。

每条 finding 包含：标题（≤80 字符、祈使句）、一段简明说明（为什么是问题、
触发条件）、`文件路径:起止行号`。评论语气务实客观，不奉承（不写"干得好"），
不夸大严重性，代码片段不超过 3 行。

按严重级分组上报：P0/P1 必报；P2 附上下文上报；P3 仅在明确有价值时上报。

末尾给出**整体正确性结论**：`补丁正确` 或 `补丁不正确` + 1-3 句理由。
判定只看阻断性问题——风格、格式、错别字等非阻断项不影响该结论。

## 第五步（可选）：修复

仅当用户明确要求"审查并修复"时执行：直接修 P0/P1；P2 描述修法交用户决定；
P3 除非顺手否则跳过。只审查时**不要**主动改代码。
