### 4.1 范围、依据与根因

- 对应 S15/S18/S26 的安全基础，以及 S01/S02/S22、F09 的已有能力保持；不是完成 M1/M2/M3/M4，也未缩减完整 79 项矩阵。

- 主要证据：锁定的 `russh 0.55.0` 的 client Handler/Handle/channel 实现，`async-ssh2-tokio 0.12.2` 的实际握手/exec/upload 边界，`russh-sftp 2.1.1` 的 server Handler 与文件 shutdown 契约；navop 借鉴点仍为主方案 N01/N02/N17/N18，不把参考项目代码复制进业务。
- **根因：** 原 service 先读取信任快照 A，但 wrapper 在真实 Host Key 回调中再次读取路径。TCP 已接受、服务端尚未发 key 时，同时把文件与服务器换成 B，wrapper 可按 B 认证；service 认证后再检查虽会拒绝发布连接，密码却已送出。原有认证后检查不能替代认证前边界。

实现边界：

- 新 `transport.rs` 为当前 `SshSession` 持有的唯一生产连接对象；exec、PTY、SFTP 都在同一 native russh handle 开 channel。`async-ssh2-tokio` 仅留在 dev-dependencies，供既有历史对照审计使用；未引入新依赖版本。
- Host Key 不匹配时仍拒绝，保留算法/公开 SHA256；不记录密码、私钥内容或签名。相同算法的冲突条目继续沿用 russh 0.55 的 fail-closed 规则，没有顺便放宽信任策略。
- 密码/私钥认证保留。私钥在验证服务器身份之后通过 blocking pool 读取；Unix Agent 分支迁到当前原生边界，但本机 Windows 无法验证该分支，**Windows OpenSSH Agent/Pageant 仍未交付**。
- exec 持续收取 stdout/stderr，不能收到 exit-status 就提前返回；非零退出保留原错误契约，缺退出码明确报错，拒绝请求释放本 channel，其他 channel 仍可用。
- `remote_push_file` 原上传能力未丢弃：复用 SFTP open/close，600 秒请求超时、64 KiB 有界读取、文件 shutdown，保留上传后 size/SHA256 检查。没有把大文件整体放进 IPC；本轮没有新做完整下载/队列/目录传输。
- **Rust 源码兼容性：** `SshSession::client/set_client` 的具体类型由 wrapper Client 改为导出的 `SshClient`；仓库内生产消费者已搜索并编译核对。Tauri command/TS DTO/持久化配置没有变更，外部直接依赖旧 Rust 具体类型者需要适配；不宣称无源码级影响。
- 本轮 UI 小修源于真实验收，不增加新开关/面板；连接设置和主工作台仍使用同一个错误格式化入口，不复制错误规则。

### 5.3 实现边界与兼容性

- 默认仍 Strict；没有应用记录的未知目标继续拒绝，不自动联网探测、接受或入库。已有 verified known_hosts 继续适用；应用公钥允许在信任文件不存在时作为独立信任源，但文件已存在而损坏/不可读/有不支持 marker 时仍拒绝，不静默忽略撤销线索。
- 应用 revoked key 优先于匹配的 known_hosts，也使已认证连接在后续复用/读写前失效；握手期间 store revision/body 变化会在发送认证材料之前拒绝。service 导入/撤销持有既有 lifecycle 写门禁，成功后主动断开该配置，再由用户重连。
- 普通导入不覆盖同算法冲突公钥，不复活 revoked；本轮没有“删除墓碑后当未知接受”的后门。轮换需要后续独立管理流程，不通过删安全断言实现。
- 当前导入只处理**已保存连接对应信任文件内、当前目标能匹配的公钥**，不是全文件批量导入：不解析 navop JSON、不实现全 Host/Match、不实现跳过明细统计。现有 known_hosts hashed-host 匹配规则保持，但这不代表主方案的批量导入已完成。
- 新 service/Tauri/TS API：`list_host_keys`、`import_host_trust(expected inspection)`、`revoke_host_key(fingerprint)`；浏览器无 Tauri 环境明确报错，不伪造成功。只回传公开算法/指纹/来源/时间/撤销标志，不返回私钥/密码。
- UI 复用 shadcn Dialog/Button/Checkbox/Label。设置连接卡片有“主机信任”；远程工作台选择连接列表右键有同一入口。目标/path 变化用 keyed owner 隔离首帧；请求 generation+pending gate 防重入和晚到回填。预览/查看无写入，确认导入先要求核验勾选，撤销再单独确认；已提交写操作不会因关闭窗口取消，文案明确提示。
- 无配置/用户数据结构破坏性迁移；旧构造函数仍支持文件信任，应用 store 通过新 builder 显式注入。安全语义变化是“主动导入的公开 key 成为应用信任、主动撤销立即断开本配置”，UI 已提示会影响 SSH/Terminal 会话；不声称远端进程因此必然终止。

### 6.3 前后端契约与安全边界

- Rust/Tauri/TS 同步新增 `ssh_begin_connection`、`ssh_respond_host_key`、`ssh_cancel_host_key`；后端只消费其保存的完整 key，UI 只回传 connection/attempt/challenge ID 与 `once/save`。响应单次消费，过期/重连/换代不可重放。
- Rust config proof 仅为进程内认证/目标配置摘要，排序 extra options，**不序列化、不写日志**；配置更新沿既有 disconnect 使挑战失效，不只比较最终字段相同与否。没有向 UI 返回密码、私钥或原始签名。
- Once 仍受信任源变化约束；保存表示明确把用户核验的 key 入库，随后的网络/认证失败不会假装撤销已提交的保存。提示明确说明提交后不能靠关闭窗口撤回；用户可在信任管理中单独撤销。
- UI controller 只有后端 connected 或确认返回成功才 resolve true；重复点击合并，取消/换目标/卸载清理未提交挑战，晚到 begin 结果不显示旧提示。正在提交时禁止取消/背板/Escape，不能把已经发出的认证伪装成已取消。清理请求失败保留诊断，服务端 TTL 仍兜底。
- Prompt 使用 shadcn Dialog/Button/Checkbox/Label，核验勾选前两个接受按钮禁用；过期后禁用并提示重新发起。服务端仍是过期判定权威，UI timer 不是安全边界；临时 UI 状态不是 persisted approval。
- 设置“测试”不再另起 strict 临时 transport：先使用同一确认 flow，再对已接受的 live connection 执行 `echo ok`；避免 Once 接受后 standalone test 重连又失败。此处 UI 显示的毫秒数是 exec 耗时，不冒称完整握手 RTT；测试成功的连接继续由既有 service 持有。
- 正常生产仍无 Insecure 选项；AcceptNew 每连接显式策略、代理/跳板身份、MFA、Windows Agent 等未在本轮实现。当前挑战只有 Direct target，不编造多路由已验。

### 9.2 数据边界与单一持久化实现

- 预览是本地只读：不联网、不认证、不创建连接配置；最多读取 **1 MiB + 1 字节**判断超限，最多 **4096 个展开条目**。注释/空行不计，合法多别名按端点计数，marker/hashed/无法解析行按一个跳过条目计数，数量口径在报告中一致。
- 状态包含 ready、重复、目标已有信任、格式/编码错误、hashed、通配/否定、不支持模式、CA、撤销声明、来源已撤销公钥、来源同算法冲突、无效 endpoint；已有目标即使公钥相同或为 revoked 也不覆盖、不添加其他算法替代它。
- 源文件中声明撤销的完整公钥，在该文件的所有普通条目中保守禁止登记，避免跳过 marker 后从另一条 plain entry 重新信任。损坏/无效编码的撤销声明直接拒绝整个预览，不能因“不知道撤销了谁”就继续导入。此保守跨目标公钥封锁是本地安全策略；不是完整 OpenSSH 撤销解释器。
- 前端只回传已展示的结构化预览、公开算法/指纹、文件摘要和数量，不决定实际 key。后端重新读取/解析并与完整预览（含 connection ID、目标/path、源 SHA256、逐条状态）一致才提交，前端改端口/改计数、源文件被替换或目标信任变化都会拒绝；真实保存始终使用后端解析的完整公钥。
- `SshHostKeyStore::import_unknown_batch` 在写入前逐目标检查当前 snapshot，再由现有 DocumentStore 的新 `compare_exchange_bodies` 执行**一个 SQLite 事务**。任一 stale CAS 或 SQL 错误不留下已写前缀；新建/替换沿同一个 SQL helper 实现，单项 CAS 保持单语句快路径，已有 embedding/created_at 保留。不是新增 run/event/审批 store。
- 成功后只断开此次实际登记涉及的同身份已保存连接，使旧 challenge/live snapshot 不能继续沿旧信任使用；未导入的连接不动。提交回执与后续连接清理结果分开，清理失败列 connection IDs，不把已经写库的公钥谎称未导入。UI 的提交回执在后续列表读取失败时仍保留。
- 大报告每页渲染 **100 条**，不一次挂载 4096 项；共享信任面板使用现有 shadcn Dialog/Button/Checkbox/Label。只有明确打开报告、勾选“已核验全部可导入指纹”并确认才写入；失败后清除旧确认入口，要求重新预览/勾选。没有新增轮询。

### 10.3 单一安全链与兼容

1. 普通 Strict/AcceptNew 连接仍拒绝 changed/revoked，普通 Once/Save 不能处理轮换 challenge；轮换 confirm 也不能把普通 unknown challenge 当轮换。用户必须进入独立管理界面。
2. 探测使用同一个 russh transport 的“始终拒绝服务器 key”handler，只做握手，不发送密码、不提供用户公钥认证、不执行命令、不保留 client；对已知 key 也不意外认证。单次探测 20 秒上限。
3. 复用已有最多 128 attempt、120 秒 monotonic TTL、单次消费的挑战库；绑定 connection/attempt/challenge、配置 proof、完整文件摘要和应用快照。配置编辑、取消、过期、跨连接、旧响应、文件变化均拒绝。
4. 确认时再次无认证探测服务器，核对 key 和信任快照后执行 CAS。服务器在弹窗后再换 key 不会被悄悄保存；确认操作本身不执行登录。提交后仍需用户手动连接，后续握手继续严格校验。
5. 本操作明确替换该 Direct host/port 的**全部旧有效密钥**，UI 列出旧/新算法与指纹并要求独立核验。来源文件不修改；旧文件条目在本应用内由对应墓碑禁用。既存 revoked key 永不恢复，其他未撤销冲突仍 fail closed。已全部撤销的目标可通过管理流程核验一个从未撤销的新 key，不会洗白旧 key。
6. 保留同目标其他历史墓碑；32 key / 32 轮换事件及 256 KiB 文档上限不静默驱逐。审计含修订号、时间、新算法/指纹、被撤销指纹，不含私钥、口令或原始签名；`rotation_history` 存储接口重开可读，尚不等于已完成通用审计 UI/API。
7. CAS 成功后清理本服务同 host/port 的全部别名连接；清理/配置持久化失败以 committed receipt 的 `disconnect_failed_ids` 独立报告，不误报信任没提交。不能通过关闭窗口撤回已提交轮换。
8. Rust facade、Tauri begin/confirm command、TypeScript DTO/API 和两个入口共享 UI 同步。旧文档的 rotations 缺省为空，无 SQL schema 迁移、新依赖或用户源文件写入。**降级注意**：旧二进制因 deny_unknown_fields 不能读取带 rotations 的目标文档，会 fail closed；不要为降级删除墓碑/审计。
9. 当前只管理 Direct；完整代理/跳板身份随 M2 实施。此切片要求 replacement 是未被当前有效信任接受的新 key；文件已更新为新 key、应用还保留冲突旧 key 等“既有 key 集合协调”仍需后续明确管理与回归，不将此限制包装成完整信任源协调完成。
