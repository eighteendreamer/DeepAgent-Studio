## 4. R002：认证前信任边界与 native transport 回归

### 4.1 范围、依据与根因

- 对应 S15/S18/S26 的安全基础，以及 S01/S02/S22、F09 的已有能力保持；不是完成 M1/M2/M3/M4，也未缩减完整 79 项矩阵。
- 起点为 R001 提交 `e47aecb3` 后的工作树，保留其已有成果，不修改原有 `docs/design/`。本轮只动 SSH crate、错误格式化及其测试、两份执行文档；不新建运行时/审批/租约/凭据库，不复制 navop 实现。
- 主要证据：锁定的 `russh 0.55.0` 的 client Handler/Handle/channel 实现，`async-ssh2-tokio 0.12.2` 的实际握手/exec/upload 边界，`russh-sftp 2.1.1` 的 server Handler 与文件 shutdown 契约；navop 借鉴点仍为主方案 N01/N02/N17/N18，不把参考项目代码复制进业务。
- **根因：** 原 service 先读取信任快照 A，但 wrapper 在真实 Host Key 回调中再次读取路径。TCP 已接受、服务端尚未发 key 时，同时把文件与服务器换成 B，wrapper 可按 B 认证；service 认证后再检查虽会拒绝发布连接，密码却已送出。原有认证后检查不能替代认证前边界。

实现边界：

- 新 `transport.rs` 为当前 `SshSession` 持有的唯一生产连接对象；exec、PTY、SFTP 都在同一 native russh handle 开 channel。`async-ssh2-tokio` 仅留在 dev-dependencies，供既有历史对照审计使用；未引入新依赖版本。
- Host Key 不匹配时仍拒绝，保留算法/公开 SHA256；不记录密码、私钥内容或签名。相同算法的冲突条目继续沿用 russh 0.55 的 fail-closed 规则，没有顺便放宽信任策略。
- 密码/私钥认证保留。私钥在验证服务器身份之后通过 blocking pool 读取；Unix Agent 分支迁到当前原生边界，但本机 Windows 无法验证该分支，**Windows OpenSSH Agent/Pageant 仍未交付**。
- exec 持续收取 stdout/stderr，不能收到 exit-status 就提前返回；非零退出保留原错误契约，缺退出码明确报错，拒绝请求释放本 channel，其他 channel 仍可用。
- `remote_push_file` 原上传能力未丢弃：复用 SFTP open/close，600 秒请求超时、64 KiB 有界读取、文件 shutdown，保留上传后 size/SHA256 检查。没有把大文件整体放进 IPC；本轮没有新做完整下载/队列/目录传输。
- **Rust 源码兼容性：** `SshSession::client/set_client` 的具体类型由 wrapper Client 改为导出的 `SshClient`；仓库内生产消费者已搜索并编译核对。Tauri command/TS DTO/持久化配置没有变更，外部直接依赖旧 Rust 具体类型者需要适配；不宣称无源码级影响。
- 本轮 UI 小修源于真实验收，不增加新开关/面板；连接设置和主工作台仍使用同一个错误格式化入口，不复制错误规则。
