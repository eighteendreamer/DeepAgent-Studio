## 核心修复

### 1. AppMobileService 重构

**问题**：原 `new()` 是同步构造函数，无法调用异步的 `register_backend()` 和 `run_discovery_loop()`。

**解决方案**：
- 将初始化拆分为两步：`new()`（同步）+ `init()`（异步）
- 使用 `std::sync::Mutex<CancellationToken>` 实现内部可变性，使 `init()` 可以接受 `&self`
- 在 `init()` 中注册 AdbBackend 并启动 discovery loop

**关键代码**：

```rust
pub struct AppMobileService {
    inner: Arc<MobileService>,
    default_timeout: Duration,
    event_tx: mpsc::UnboundedSender<MobileEvent>,
    _event_rx: mpsc::UnboundedReceiver<MobileEvent>,
    cancel_token: std::sync::Mutex<CancellationToken>,
}

impl AppMobileService {
    pub fn new() -> Self {
        // 创建基础结构，不注册 backend
        let (event_tx, event_rx) = mpsc::unbounded_channel::<MobileEvent>();
        let registry = DeviceRegistry::new(event_tx.clone());
        // ...
        Self {
            inner: Arc::new(inner),
            event_tx,
            _event_rx: event_rx,
            cancel_token: std::sync::Mutex::new(CancellationToken::new()),
        }
    }

    pub async fn init(&self) {
        // 创建并注册 AdbBackend
        let resolver = ToolResolver::new();
        let runner = std::sync::Arc::new(SystemAdbRunner::new());
        let adb_backend = AdbBackend::new(resolver, runner);
        
        self.inner
            .register_backend(MobilePlatform::Android, Box::new(adb_backend))
            .await;

        // 启动 discovery loop
        let cancel_token = CancellationToken::new();
        let backend_for_discovery = std::sync::Arc::new(AdbBackend::new(
            ToolResolver::new(),
            std::sync::Arc::new(SystemAdbRunner::new()),
        ));
        
        tokio::spawn(deepagent_mobile_runtime::run_discovery_loop(
            backend_for_discovery,
            Arc::new(self.inner.registry().clone()),
            DiscoveryConfig::default(),
            cancel_token.clone(),
            self.event_tx.clone(),
        ));

        // 存储 cancel token
        if let Ok(mut token) = self.cancel_token.lock() {
            *token = cancel_token;
        }
    }
}
```

### 2. Tauri Setup 集成

**问题**：Tauri 的 `setup` 闭包不是 async，无法直接调用 `init().await`。

**解决方案**：在 setup 中 spawn 一个异步任务来调用 `init()`。

```rust
// Initialize mobile service with Android backend and discovery
let mobile_service = Arc::new(AppMobileService::new());
let mobile_service_for_init = mobile_service.clone();
tauri::async_runtime::spawn(async move {
    mobile_service_for_init.init().await;
});

app.manage(AppState {
    // ...
    mobile: mobile_service,
    // ...
});
```

## 设计决策

### 1. 为什么使用两步初始化？

**选项 A**：使 `new()` 为 async
- ❌ 破坏 API 兼容性
- ❌ 需要在所有调用点使用 `.await`
- ❌ 无法在同步上下文中创建

**选项 B**：使用 `block_in_place` 在 `new()` 中阻塞
- ❌ 需要多线程 runtime，测试环境（current-thread）会 panic
- ❌ 在 async 上下文中阻塞是反模式

**选项 C**：拆分为 `new()` + `init()` ✓
- ✅ 保持 `new()` 同步，兼容所有上下文
- ✅ `init()` 异步，可以正确调用异步方法
- ✅ 使用内部可变性（Mutex）使 `init()` 接受 `&self`
- ✅ 可以在 Arc 包裹后调用

### 2. 为什么使用 Mutex<CancellationToken>？

`init()` 需要存储 cancel_token 以便后续取消 discovery loop。但 `init()` 接受 `&self`（为了能在 Arc 包裹后调用），因此需要内部可变性。

`std::sync::Mutex` 是最简单的选择：
- 只在 `init()` 时写入一次
- 不会在运行时频繁锁定
- 不需要异步锁（tokio::sync::Mutex）

### 3. 为什么 spawn 两次 AdbBackend？

代码中创建了两个 AdbBackend 实例：
1. 一个用于 `register_backend()`（注册到 MobileService）
2. 一个用于 `run_discovery_loop()`（discovery 专用）

**原因**：
- `register_backend()` 需要 `Box<dyn MobileBackend>`（所有权转移）
- `run_discovery_loop()` 需要 `Arc<dyn MobileBackend>`（共享引用）
- 两者生命周期和用途不同，共享同一个实例会增加复杂度

**优化空间**：可以重构为共享同一个 Arc<AdbBackend>，但当前实现更清晰。

1. **两步初始化模式**：`new()`（同步）+ `init()`（异步），解决了构造函数无法调用异步方法的问题。

3. **异步 spawn**：在 Tauri setup 中 spawn 异步任务调用 `init()`，避免了 setup 闭包不是 async 的问题。
