# DeepAgent Studio 移动端预览调试执行方案（M18 重定版）

> 适用对象：DeepAgent Studio 当前代码库
> 起点状态：M18 已修复 Android backend 注册与 discovery loop 启动
> 结论先行：旧方案的顺序已经失效，必须按本方案重新推进

## 1. 这份方案解决什么问题

这是一份从当前真实状态出发的执行方案，不是最初架构稿的继续扩写。

当前系统已经有了移动端基础 crate、Android backend、Emulator 生命周期、Tauri 命令、前端 DTO、M18 启动接入，但这些能力还没有形成你要求的三个真实目标闭环：

1. 系统启动后，真实发现并访问 USB 真机或模拟器，能打开页面并显示真实画面；
2. 通过 USB 或模拟器拿到完整 UI 结构，而不是摘要；
3. 通过 USB 或模拟器抓到真实接口请求、响应结构和参数。

因此，本方案只接受“真实验收驱动”的推进方式，不接受继续扩 iOS、Remote Mac、App SDK 或新的前端调试页面来替代这三个目标。

## 2. 当前基线

当前基线只认下面这些事实：

- `AppMobileService::init()` 已在桌面启动时注册 Android backend，并启动 discovery loop；
- Android 侧已有 backend / emulator / snapshot / log / artifact 相关实现；
- `mobile_ui_snapshot` 目前仍只返回摘要 DTO，不是完整 UI tree；
- 网络侧目前只有协议模型和脱敏能力，没有通用抓包闭环；
- Agent 层仍存在第二套 `MobileBackend` trait 风险，需要后续收敛；
- 真实 USB 真机、真实 Emulator 的端到端证据还没有补齐。

这意味着，当前最合理的计划不是“继续造新能力”，而是“把现有链路验收成真”。

## 3. 最高级推进原则

### 3.1 只允许一条主线

所有移动端能力必须沿着这条链路推进：

`MobileService -> MobileRuntime -> Android/iOS Backend -> 官方设备探测接口 -> DeviceRegistry -> MobileEvent -> Tauri/React/Agent`

任何绕过这条链路的做法都视为偏航，包括但不限于：

- Agent 自己扫描 USB；
- 直接在工具层拼 shell；
- 用项目专用日志、截图 OCR、固定 JSON 或业务埋点假装完成抓包；
- 用摘要、静态样本或 fake backend 假装完整 UI 树；
- 为某一个被测项目写硬编码适配。

### 3.2 只按目标顺序推进

严格顺序固定如下：

1. 目标一：设备发现、USB/模拟器连接、页面启动、真实截图、断开重连；
2. 目标二：完整 UI 结构；
3. 目标三：通用网络观测。

目标一没有真实验收前，不允许继续做 UI Inspector。
目标二没有验收前，不允许宣称 Agent 能可靠操作。
目标三没有验收前，不允许宣称网络调试完成。

### 3.3 每轮必须闭环

每一轮任务必须同时完成这六件事：

1. 说明本轮范围、受影响模块、不修改范围、验收目标；
2. 先查证现有代码、配置、调用方、测试和官方行为；
3. 只做一个可验证的根因修复或一个完整垂直切片；
4. 跑与本轮变更匹配的格式、编译、测试或真实设备验证；
5. 回头检查 diff、状态机、错误路径、取消/超时、权限、脱敏、事件持久化和跨层契约；
6. 按 100 分制评分，记录通过项、失败项、未执行项、证据和下一步。

低于 90 分，不得进入下一阶段。

## 4. 现在开始，先冻结哪些东西

在目标一通过前，以下方向全部冻结：

- iOS / Remote Mac / App SDK 新功能；
- React 新页面和新交互；
- 新的 Tauri command，除非它是目标一的必要证据；
- 新的 mobile 专用 trait、第二套状态机、第二套事件中心；
- 对某个项目的包名、页面名、接口名、控件文本做特判；
- 用 mock、OCR、静态 JSON、退出码、业务日志替代真实设备证据。

## 5. 目标一：先把 Android 真闭环做实

### 5.1 目标定义

目标一不是“代码能跑”，而是下面这组事实都能被真实证明：

- 系统启动后自动发现设备；
- USB 真机和模拟器都能进入设备列表；
- 设备状态能从离线、未授权、启动中、就绪等状态正确变化；
- 可以打开一个已安装应用并看到真实画面；
- 可以截图并拿到真实 artifact；
- 设备插拔、模拟器启动/停止、授权变化可以被系统内部发现；
- 断开后能正确移除或标记，重连后能恢复。

### 5.2 目标一的交付物

每一轮只做一类真实闭环，不要把多个难点混在一轮里：

1. 启动接入检查：确认 `MobileService` 在桌面启动时确实带着 Android backend 和 discovery loop；
2. 真实设备发现：用一个真实 USB 真机和一个真实 Emulator 跑通发现；
3. 真实页面显示：用已编译项目证明打开页面并截图；
4. 生命周期闭环：安装、启动、停止、断开、重连；
5. 真实证据报告：设备型号、系统版本、工具版本、连接方式、步骤、日志、artifact、评分。

### 5.3 目标一的完成标准

以下内容必须同时成立：

- `mobile_list_devices` 返回真实设备，不是 fake；
- `mobile_backend_status` 不只是“backend 存在”，而是说明实际工具链可用；
- `mobile_screenshot` 返回真实 artifact；
- `mobile_launch_app` / `mobile_stop_app` 对真实设备有效；
- 断开 / 重连后列表状态会真实更新；
- 报告里给出真实设备与模拟器的证据位置。

只证明 `adb` 命令退出码为 0，不算完成。

## 6. 目标二：完整 UI 结构

### 6.1 目标定义

目标二要求的是完整树，不是眼前可见的一小部分。

必须能证明：

- 一次 snapshot 返回完整 hierarchy；
- 节点有稳定的 `snapshot_id` / `node_id`；
- 节点属性、父子关系、数量和边界可验证；
- 节点查询可复现；
- snapshot 过期后会被安全拒绝。

### 6.2 当前限制

当前前端和 Tauri 边界还在返回 summary，不满足目标二。

所以目标二的第一件事，不是做更多 UI 页面，而是把完整树的协议、后端投影和前端消费链路补齐。

### 6.3 目标二的验收材料

- 完整 UI 树示例；
- 真实设备上的节点数量和层级深度；
- 查询与失效的真实验证；
- 手工和自动化测试结果；
- 复查 diff，确认没有把摘要当成完整树。

## 7. 目标三：通用网络观测

### 7.1 目标定义

目标三要求的是通用观测链，不是某个项目的专用埋点。

必须能证明：

- 请求和响应成对关联；
- 能拿到方法、URL、参数、请求头脱敏结果、响应状态、响应头脱敏结果、响应结构、耗时、错误和序号；
- 证据来自通用平台 / 应用调试能力，而不是被测项目自己加日志；
- 能在 USB 真机和模拟器上工作。

### 7.2 当前限制

现在只有数据模型和脱敏测试，没有完整采集链。

所以目标三的第一步不是补 UI，而是先把真实采集来源、生命周期、artifact、事件投影和权限边界补齐。

## 8. 分阶段执行路线

### Phase A：把目标一做成可验收闭环

只做下面这些事：

- 确认系统启动会自动注册 Android backend；
- 确认 discovery loop 真的在跑；
- 补齐真实 USB 真机和真实 Emulator 的发现证据；
- 补齐页面启动、截图、断开、重连证据；
- 生成目标一真实验收报告。

### Phase B：把 UI 树做成完整树

只在 Phase A 通过后开始：

- 把 summary 改成完整树投影；
- 补节点查询和失效拒绝；
- 补真实 UI hierarchy 证据；
- 生成目标二验收报告。

### Phase C：把网络观测做成通用链

只在 Phase B 通过后开始：

- 补统一采集入口；
- 补请求 / 响应关联；
- 补脱敏、限长、artifact、事件投影；
- 生成目标三验收报告。

### Phase D：再考虑 iOS / Remote Mac / App SDK

只有在 Android 三目标都通过后，才允许重启这些方向。

它们不是当前主线，不能抢占目标一、二、三的资源。

## 9. 每轮必须产出的文档

每轮都要留一份简短但完整的阶段记录，至少包含：

- 本轮目标；
- 修改文件；
- 依据来源；
- 实际命令；
- 自动化测试结果；
- 真实设备 / 模拟器型号和系统版本；
- USB / 模拟连接方式；
- 三项目标得分；
- 总分；
- 失败证据；
- 未执行验证；
- 偏离风险；
- 是否存在项目特判；
- 下一轮唯一建议动作。

## 10. 明确禁止的偷懒方式

以下内容一律不能当成果：

- fake backend 测出来的结论；
- 单元测试通过就宣布完成真实设备验收；
- 只靠协议类型、序列化测试、UI 摘要、OCR 或固定节点样例；
- 用项目内埋点冒充网络抓包；
- 继续加 iOS / Remote Mac / App SDK 来证明 Android 已完成；
- 让 Agent 自己找设备、自己猜 serial、自己扫 USB；
- 修改被测项目源码来制造“支持成功”。

## 11. 当前建议的唯一下一步

现在不要再扩散功能面。

下一步唯一值得做的是：**把目标一补成真实验收文档和真实设备证据**。

如果要继续开发，就按这条顺序：

1. 先跑真实 USB 真机和真实 Emulator；
2. 再把设备发现和页面显示证据补齐；
3. 再处理完整 UI 树；
4. 再处理网络抓包；
5. 最后才轮到 iOS / Remote Mac / App SDK。
